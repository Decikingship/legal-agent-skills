# 专家编写规范与模板

> **专家只做编排，不承载法律知识。** 所有法律知识、检索方法、输出格式都在 skill 里。这条界限一旦破坏，同一份知识会在多个专家里出现不同版本，修一处漏三处。
>
> 判断标准：如果你在专家文件里写下了任何一条具体的法律规则、检索技巧或输出格式，说明它应该被移到某个 skill 里去。

---

## 一、专家与 skill 的分工

| | Skill | 专家 |
|---|---|---|
| 职责 | 一件事做到位 | 把若干件事按正确顺序串起来 |
| 内容 | 法律知识、检索策略、输出格式 | 流程、澄清、门禁、降级 |
| 复用 | 被多个专家复用 | 不被复用，对应一个具体交付场景 |
| 组合 | —— | 封闭，5–9 个 skill |

**为什么专家是封闭组合**：律师需要可预期的交付。同一个专家每次跑出来的东西结构应当一致，才能进入事务所的工作流。开放式的动态选取会导致交付物形态漂移。

---

## 二、专家规模控制

- **5–9 个 skill**。少于 5 个说明这个场景用单 skill 就够了，不必包装成专家；多于 9 个说明场景切得太粗，应当拆成两个专家
- **对应一个真实交付物**。专家的名字应该能对上律师工作台账里的一个条目：一份类案检索报告、一份合同审查意见、一份尽调报告。不要造「诉讼助手」这种指向模糊的专家
- **执行时长可预期**。如果一个专家要跑十几分钟，考虑拆成「快速版」和「深度版」两个

---

## 三、`.expert` 打包格式（平台真实格式）

`.expert` 是 zip 包，**技能打包在专家内部，专家自包含**：

```
<专家名>.expert  (zip)
├── EXPERT.md
└── skills/
    ├── <dir1>/          # 完整 skill 目录：SKILL.md + scripts/ + references/ + evals/
    ├── <dir2>/
    └── ...
```

### EXPERT.md frontmatter

```yaml
---
name: 类案检索与分析专家
description: <AI 靠它判断何时把任务委派给这个专家，写清适用场景。推销式写法，含中文口语触发词>
expose-process: true        # 是否向用户展示执行过程
enable-thinking: true       # 是否开启思考
reasoning-effort: high      # 推理强度
category: tools
skills:
- kind: bundled
  dir: zhihe-law-search     # skills/ 下的目录名
  name: 智合AI搜法           # 对应 SKILL.md 里的 name 字段
- kind: bundled
  dir: lit-search-similar-cases
  name: lit-search-similar-cases
format: zhihe-expert/1
---

<专家提示词正文：决定语气与工作方式，即本文件第四节的编排内容>
```

### ⚠️ 目录名必须自己指定，不要依赖平台生成

平台从 `name` 字段 slugify 出目录名。**中文名会被丢掉**——`智合AI搜法` → `ai`，第二个中文名 skill 撞名后变 `ai-2`。

后果：
1. 目录名无语义，事后打开包认不出是哪个 skill
2. **顺序依赖**：上传顺序变了，`ai` 与 `ai-2` 就对调，而 `dir → name` 映射不会跟着变
3. 构建产出的规范目录名被丢弃

**做法**：用 `build_skills.py --expert` 自行打包，显式指定 `dir` 为规范英文名，`name` 保持原样（中文名不改，平台内引用不断）。

## 四、专家模板

````markdown
---
name: expert-<英文短横线名>
description: <这个专家解决什么交付场景，何时派它出场。同样需要推销式写法，
  列举律师会说的原话。写清楚与相邻专家的分工边界。>
---

# <中文专家名>

## 交付物
一句话说清最终产出。要具体到律师能想象出这份东西长什么样。
例：一份符合《类案检索指导意见》格式、可直接附卷提交的类案检索报告。

## 适用场景 / 不适用场景
| 情形 | 处置 |
|---|---|
| <该派本专家的情形> | 本专家 |
| <相邻情形> | 改派 expert-XXX |

## 组成 skill（封闭清单）

| 顺序 | Skill | 在本流程中的角色 |
|---|---|---|
| 1 | <skill-name> | <承担哪一步> |
| … | | |
| 门禁 | core-verify-statute-validity | 法条效力校验 |
| 门禁 | core-verify-case-citation | 案例真实性校验 |
| 门禁 | core-claim-evidence-audit | 结论—依据一致性审查 |

## 开工前澄清

必须先确认的信息，**一次性问完**：
1. <信息项>：<为什么必需，缺了会导致什么错误>

**追问话术**：<可直接使用的文本，简洁专业>

用户明确表示"先跑起来看看"时，用默认值推进，但在输出中标注哪些结论基于假设。

## 执行流程

### 阶段一：<阶段名>
- 调用：<skill>
- 输入：<从上一阶段拿到什么>
- 产出：<传给下一阶段什么>
- 阶段结论：<这一阶段要回答的问题>

### 阶段二：……

### 阶段 N：质量门禁
- 调用校验 skill
- 校验不通过的处置见下

## 质量门禁

| 节点 | 校验内容 | 不通过时 |
|---|---|---|
| 检索完成后 | 法条效力、案例终局性 | 剔除失效项并重新检索补足 |
| 生成前 | 要素完整性 | 回到澄清环节追问 |
| 输出前 | 结论—依据一致性 | 删除无依据的结论，不得保留 |

**门禁不通过时，宁可交付一份不完整但可靠的东西，也不要交付一份完整但含幻觉的东西。** 律师能处理"这部分没查到"，处理不了"引用了一个不存在的案例"。

## 失败与降级

| 情形 | 处置 |
|---|---|
| 检索无结果 | 如实说明已尝试的检索路径，说明可能原因（该领域无明文规定 / 该问题尚无判例），不用通用知识填补 |
| 关键要素缺失且用户无法提供 | 给出有条件结论，明确标注前提假设 |
| 问题超出专家能力边界 | 明确说明边界在哪，指出需要人工处理或需要其他专家的部分 |
| 检索结果内部冲突 | 如实呈现冲突，标注为【争议】，给出各方依据 |

## 中间产物

说明哪些中间结果需要保留给用户看：
- 检索痕迹（检索词、命中量、筛选过程）—— 律师需要评估检索充分性
- 被排除的材料及排除理由 —— 律师可能不同意你的排除判断
- 待确认事项清单

## 与其他专家的衔接

说明本专家的输出可以作为哪些专家的输入，避免用户重复提供信息。
例：类案检索专家的输出可直接作为一审代理专家写代理词的依据来源。
````

## 五、编排原则

### 4.1 检索在前，生成在后

任何专家的流程都是「澄清 → 检索 → 分析 → 生成 → 校验」。**不允许先生成再补依据**。先生成的文本会锚定后续检索方向，导致只找支持性材料。

### 4.2 校验是门禁不是装饰

校验 skill 必须放在能拦住问题的位置——生成之前校验法条效力，输出之前校验结论依据。放在最后走个过场没有意义。

### 4.3 阶段间传递结构化结果

阶段之间传递的应当是结构化的中间产物（争议焦点清单、法条清单、案例清单），不是自然语言总结。总结会丢失案号、条文序号这类必须精确的信息。

### 4.4 立场参数要贯穿全程

涉及对抗性场景的专家（合同审查、诉讼），立场（甲方/乙方/中立、原告/被告）必须在澄清阶段确定，并传递给每一个 skill。中途换立场或立场不明会产出自相矛盾的意见。

## 六、交付前检查

- [ ] 专家文件里没有任何具体的法律规则、检索技巧或输出格式（都在 skill 里）
- [ ] skill 数量在 5–9 之间
- [ ] 交付物描述具体到律师能想象出形态
- [ ] 澄清问题一次性问完，有可直接使用的话术
- [ ] 校验 skill 挂在了能拦住问题的位置，不是流程末尾走过场
- [ ] 有明确的失败降级路径，且降级方向是"少而可靠"不是"多而含幻觉"
- [ ] 写明了与相邻专家的分工边界
- [ ] 所有引用的 skill 都已经建成（不能依赖尚未开发的 skill）
- [ ] `EXPERT.md` 的 `skills[].dir` 与 `skills/` 下的实际目录名一一对应
- [ ] `skills[].name` 与各 `SKILL.md` 的 `name` 字段完全一致
- [ ] 目录名为规范英文名，**未使用平台 slugify 出的 `ai`、`ai-2` 之类**
- [ ] **description 已写明「委派前请先与用户确认」及具体要素**
- [ ] **正文有「要素缺失时」的处置规则**，未写「开工前澄清」这类假定可提问的话
- [ ] 涉及立场的，降级行为具体可执行（如并列给出三个立场）
