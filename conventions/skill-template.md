# Skill 编写规范与模板

> 写 skill 时把力气花在「检索策略」和「强制校验项」两节。法律 skill 的价值不在文字漂亮，在于约束检索的准确性和引用的可靠性——这两点是通用大模型做不到的，也是用户付费的理由。

---

## 一、目录结构

```
<skill-name>/
├── SKILL.md          必需
├── references/       可选，正文放不下的细节（条款库、格式规范、领域知识）
├── scripts/          可选，确定性计算（利息、期间、赔偿测算）
├── assets/           可选，输出用的模板文件（docx 模板、条款范本）
└── evals/
    └── evals.json    测试用例
```

## 命名：目录用英文，name 用中文

**两者分离，各司其职：**

| | 用途 | 语言 | 例 |
|---|---|---|---|
| **目录名 / `dir`** | 稳定标识，用于构建、依赖注入、排障 | 英文 `域-动作-对象` | `lit-search-similar-cases` |
| **`name` 字段** | 展示名称，用户在技能列表里看到的 | 中文，动宾结构，4–8 字 | `类案检索` |

**为什么目录必须英文**：平台从中文 `name` slugify 出目录名时会丢掉中文，`智合AI搜法` 变成 `ai`，第二个撞名变 `ai-2`——无语义，且随上传顺序漂移。`.expert` 清单的 `dir` 与 `name` 本就是两个字段，天然支持分离。

**为什么 name 必须中文**：面向中国法律从业者的产品，用户在专家的技能列表里看到 `lit-analyze-judgment-divergence` 只能猜。中文名是产品可用性问题，不是审美问题。

**中文名的要求**：
- 动宾结构，一眼看出做什么：`裁判规则提炼` 而不是 `规则模块`
- 与同类 skill 可区分：`类案检索`（找案例）vs `案例援引审查`（查引用对不对）
- 不与通用术语混淆时用「」包裹交叉引用——正文里的「类案检索」是 skill，类案检索是活动
- SKILL.md 正文一级标题下补一行 `> 技术标识：\`<目录名>\``，便于运维定位

英文目录的命名规则 `域-动作-对象`：

| 前缀 | 域 |
|---|---|
| `core-` | 底座与校验 |
| `lit-` | 诉讼 |
| `nonlit-` | 非诉 |
| `util-` | 工具 |

例：`core-verify-statute-validity`、`lit-search-similar-cases`、`nonlit-review-contract`、`util-legal-calculator`。

## 二、description 写法（触发成败全在这一句）

Claude 有明显的**欠触发**倾向——skill 写得再好，描述保守就等于不存在。写描述时：

1. **推销式表述**：写「务必在用户提到 X、Y、Z 时使用本 skill」，而不是「用于处理 X」
2. **穷举中文口语触发词**：律师不会说「请调用类案检索技能」，他们说「查一下有没有类似判例」「本地法院一般怎么判」「这种案子胜诉率高吗」。把这些原话写进去
3. **写清不触发的情形**，并指向正确的兄弟 skill，避免技能间互相抢活
4. **英文关键词也带上**：部分用户会中英混用

**反例**：
```
description: 用于检索类案。
```

**正例**：
```
description: 检索并输出符合《类案检索指导意见》格式的类案检索报告，按四级效力位阶
  组织案例、提炼裁判规则、主动排查不利判例。务必在用户提到"查类案""有没有类似
  判决""本地法院怎么判""这种案子一般判多少""胜诉率""裁判尺度""同案不同判"
  "similar cases""precedent"时使用本 skill，即使用户没有说出"类案检索"四个字。
  用户只是想查某条法律怎么规定时，改用 core-retrieval-strategy；用户要写文书时，
  本 skill 作为前置检索环节被调用。
```

## 四、写作风格

- **祈使句**，不用「可以考虑……」这类软表述
- **解释为什么**，不要堆砌大写的 MUST。说明理由后模型执行得更稳
- **通用化**，不要把 skill 写得只能处理示例里的那种案子
- **控制篇幅**：SKILL.md 不超过 500 行。逼近上限时把细节下沉到 `references/`，正文写清「何时去读哪个文件」
- **先写草稿，再用新眼光重读一遍改**。第一稿总有堆砌

## 五、测试用例

写完草稿后，准备 2–3 条测试 prompt，存到 `evals/evals.json`：

```json
{
  "skill_name": "lit-search-similar-cases",
  "evals": [
    {
      "id": 1,
      "prompt": "客户下周开庭，买卖合同纠纷，对方主张违约金按合同总价 30% 计算，我方认为过高。帮我查一下江苏地区近三年法院对违约金调整的尺度。",
      "expected_output": "按效力位阶组织的类案检索报告，含江苏地区裁判尺度分布区间与调减比例统计"
    }
  ]
}
```

**测试 prompt 要有分量。** 「读一下这个文件」这类单步任务根本不会触发 skill，测不出任何东西。要写律师真实会说的、多步骤的、带具体案情要素的话。

三条测试用例的覆盖建议：
1. **典型场景** —— 要素齐全的标准用法
2. **要素缺失** —— 检验是否会追问而不是瞎猜
3. **边界或陷阱** —— 涉及已修法领域、无明确规定的争议问题、或检索应当无果的情形，检验会不会编
